# Git Commit 规则

## 授权边界

- 只有用户明确要求创建提交时才执行 `git add`、`git commit`。仅要求拆分规划、提交信息或就绪
  审查不授予写入暂存区和历史的权限；amend、rebase、push、tag 等操作需要单独明确授权。
- 编码任务完成不等于自动获得提交授权。
- 提交前检查 `git status --short` 和相关 diff，只暂存本次任务文件，保留用户的其他改动。
- 同时检查已暂存和未暂存 diff。只对本次路径执行 `git add` 仍可能让普通 `git commit` 带入原有
  暂存内容；必须核对完整提交候选，保留无关暂存项。同文件混有其他修改时按 hunk 隔离。
- 不用 `git add .`、`git add -A`、reset、restore 或 stash 简化提交范围；不绕过失败的 hook。

## 隔离提交

暂存区里已有与本任务无关的内容（其他会话、其他任务或手动暂存）时，普通 `git commit` 会把这些内容
一并提交。

- 默认采用隔离提交：`git commit --only -F <消息文件> -- <本次路径…>`。Git 会为这次提交生成临时索引，
  只写入指定路径的工作区内容，其他暂存条目保持原样。
- 只对本任务完整拥有的文件使用；文件内混有其他改动时不要整文件提交，无法安全分离则保留该文件，
  在结果里说明其归属。
- 提交前后核对范围：`git show --stat --oneline HEAD` 的文件应与本次路径一致；对无关的已暂存路径比较
  `git rev-parse :<path>` 与 `git hash-object <path>`，确认既不进入提交也不被改写。
- pre-commit 的 lint-staged 只处理临时索引中的文件；工作区内容与预期提交内容不一致的文件不要纳入，
  否则钩子可能把额外改动写进提交。
- `.git/index.lock` 已存在时先确认是否还有 git 进程；只清理确认无进程且明显陈旧的锁，不要删除其他
  会话正在使用的锁。

## 提交格式

```text
<emoji> <中文描述>
```

- 每条提交只用一个 Unicode emoji。
- 标题与正文使用中文；按本次实际 diff 的主要目的选 emoji，不从历史提交推断或模仿风格。
- 描述以动词开头，单行不超过 100 个字符。
- 不添加 `feat:`、`fix(scope):` 等 Conventional Commits 前缀。
- 每个提交只表达一个可独立理解的主题；按行为边界拆分，不要仅按文件机械拆分。
- 同一行为的实现、必要配置、回归测试和文档通常放在一起。先完成并验证该单元，再提交下一单元。

## 常用 Emoji

下表是常用示例，不是允许列表；选择方法与语义边界见
`../skills/git-workflow/references/commit-conventions.md`。

| Emoji | 用途     | Emoji | 用途          |
| ----- | -------- | ----- | ------------- |
| ✨    | 新功能   | 🐛    | Bug 修复      |
| 🩹    | 小修复   | ♻️    | 重构          |
| ⚡️    | 性能     | 💄    | UI/样式       |
| 📝    | 文档     | 🎨    | 格式/结构     |
| 🔧    | 配置     | 🗃️    | 数据库        |
| 🏷️    | 类型     | ✅    | 测试          |
| ➕    | 添加依赖 | ➖    | 删除依赖      |
| ⬆️    | 升级依赖 | 🔥    | 删除代码/文件 |
| 📦    | 构建     | 🚀    | 部署          |

示例：

```text
✨ 添加用户个人页面跳转功能
🐛 修复角色生日判断逻辑
♻️ 重构数据库事务处理
📝 迁移 Agents 项目规范
```
